# Brain ↔ Business-System Context Capability Protocol (Canonical Stage F)

This document defines the generic wire protocol and architectural boundary allowing ANY independent Business System to act as a Context Capability Provider for Aaram Brain. It enforces the Stage F generic capability framework invariants without leaking Python implementations or domain-specific logic across boundaries.

---

## A. Brain ↔ Business System Protocol Architecture

The protocol operates as a stateless Request/Response interaction over a generic transport boundary (e.g., HTTP or gRPC). The wire format is JSON. 

**Architectural Ownership:**
- **Brain Owns:** The generic protocol, gateway abstraction, capability routing, orchestration, and transport failure handling.
- **Business System Owns:** Capability URNs, capability metadata declarations, semantic interpretation, constraint-to-physical translation, business rules, physical truth, and evidence construction.

Business Systems implement this protocol completely independently. They **must not** import Brain Core Python classes.

---

## B. Canonical Request Contract (Brain → Business System)

When Brain resolves an intent to a specific Capability URN, the `ContextCapabilityGateway` transmits a JSON POST request.

**Headers:**
- `X-Correlation-ID`: Trace identifier for observability.
- `Authorization`: Bearer token (propagated untouched by Brain).

**Payload (`ResolvedSemanticRequirement`):**
```json
{
  "capability_urn": "urn:generic:capability:identifier",
  "requirement": {
    "requirement_id": "req-uuid-1234",
    "original_requirement": {
      "semantic_intent": "Generic natural language description of the requirement"
    },
    "core_identities": ["domain.entity.concept"],
    "semantic_constraints": [
      {
        "identity": "domain.entity.concept",
        "operator": "EQUALS",
        "bound_value": "example-value"
      },
      {
        "identity": "domain.temporal.range",
        "operator": "GREATER_THAN",
        "bound_value": "2026-08-01T00:00:00Z"
      }
    ]
  }
}
```
*Correction Applied: `preferred_source_urn` has been completely eliminated. Cognitive Planning and transport are strictly source-blind. The canonical Stage F SemanticConstraint structure (identity, operator, bound_value) is preserved.*

## C. Canonical Response Contract (Business System → Brain)

The Business System returns a `ContextCapabilityResult` JSON object.

**Payload:**
```json
{
  "status": "SUCCESS",
  "data": {
    "key": "value" 
  },
  "provenance_metadata": {
    "retrieval_timestamp": "2026-08-28T21:40:00Z",
    "business_timestamp": "2026-08-28T21:40:00Z",
    "derivation_metadata": "Computed via internal aggregation"
  },
  "error_message": null
}
```
*Note: The `data` payload is completely opaque to Brain. Brain stores it blindly as an `EvidenceItem`.*

## D. Generic Registration / Discovery Contract

To route requests, Brain's `CapabilityResolver` requires rich metadata, while the `ContextCapabilityGateway` requires physical transport endpoints. Registration provides BOTH without hardcoding domains into Brain Core.

**Configuration Payload (e.g., JSON/YAML config loaded at Brain startup):**
```json
{
  "capabilities": [
    {
      "capability_urn": "urn:generic:capability:identifier",
      "endpoint_url": "https://external.system.internal/api/exposure/invoke",
      "metadata": {
        "provides_identities": ["domain.entity.concept", "domain.temporal.range"],
        "supported_constraint_types": ["ENTITY", "TEMPORAL"]
      }
    }
  ]
}
```
Brain Core loads this configuration, registering the URN and `metadata` with the `ProviderRegistry` for semantic subset matching, and registering the `endpoint_url` with the `ContextCapabilityGateway` for physical routing.

## E. Transport vs. Capability Failure Model

Failure semantics are strictly demarcated to preserve the boundary between transport infrastructure and business truth.

**1. Transport / Infrastructure Failures (Generated by Brain Gateway):**
- **Network Timeout / 5xx HTTP Error**: Transport failed. No `ContextCapabilityResult` is received. Brain Orchestrator handles this via retry or marks the requirement as `PROVIDER_EXECUTION_ERROR`.

**2. Capability Execution Semantics (Generated by Business System):**
- **`SUCCESS` with populated `data`**: The constraint matched physical records, and data was retrieved.
- **`SUCCESS` with empty `data` (e.g., `{}`)**: The evaluation succeeded correctly, but the physical answer is legitimately "zero records" or "none" (e.g., a query for orders that legitimately do not exist).
- **`DATA_UNAVAILABLE`**: The capability cannot definitively answer due to missing internal systemic prerequisites (e.g., a required internal ledger is offline, or the requested semantic constraint maps to a column that is currently corrupted/unindexed). It explicitly does NOT just mean "zero results".
- **`UNAUTHORIZED`**: The caller's propagated identity lacks RBAC privileges to access the requested physical data.
- **`ERROR`**: The Business System encountered an internal fault parsing the constraint or executing its business rules.

## F. Security / Auth Propagation
- Brain possesses an authorization token (e.g., User JWT or M2M Service Token) representing the caller's context.
- Brain blindly propagates this token in the `Authorization` header.
- The Business System Context Exposure Module (CEM) assumes full and exclusive responsibility for verifying the token and enforcing RBAC against its own physical data. Brain enforces zero RBAC for Business Systems.

---

## G. Versioning Model
- **Protocol Envelope:** Any change to the JSON schema of `ContextCapabilityResult` requires a Brain Core version bump.
- **Capabilities & Semantics:** Business Systems can version their capabilities completely independently via URNs (e.g., `urn:generic:capability:identifier:v2`). Azm semantic identities (e.g., `domain.entity.concept.v2`) can evolve independently. The Brain transport socket remains utterly unaware of these version changes.

---

## H. Business-System Implementation Boundary
An external Business System must implement a **Context Exposure Module (CEM)**.
1. It exposes a web server endpoint accepting the generic JSON request.
2. It parses `identity`, `operator`, and `bound_value` from the JSON.
3. It maps `identity` strings to internal physical columns, ORM models, or API parameters.
4. It executes physical queries securely against its own databases.
5. It returns the JSON `ContextCapabilityResult` containing the opaque `data` dictionary.

## I. Zero-Touch Future-Domain Proof
**Scenario:** An entirely unknown future domain, `AaramLogistics`, needs to integrate with Brain to provide "Fleet Location" intelligence.

**Proof of Zero-Touch Integration:**
1. `AaramLogistics` independently defines its URN (`urn:logistics:capability:fleet_location`) and metadata.
2. `AaramLogistics` builds a CEM HTTP endpoint parsing generic semantic constraints and querying its physical PostgreSQL database.
3. The Ops team adds the new URN, metadata, and endpoint URL to Brain's `capabilities.json` configuration file.
4. Brain restarts, loads the configuration, and immediately begins matching NLP requirements to the new URN and POSTing JSON payloads to the Logistics endpoint.
**Result:** `AaramLogistics` is fully integrated. Zero Brain Core Python files were modified. Zero `AaramLogistics` schemas leaked into Brain.

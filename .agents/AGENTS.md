# Aaram_Inventory AI Agent Rules

- **Foundation Layer Freeze**: The `src/foundation/` layer is explicitly FROZEN. Do NOT modify any code in this layer unless explicitly instructed by the user with a compelling reason. The architecture is locked and must act strictly as generic, reusable infrastructure for the business domains.
- **Versioning Strategy**: `APP_VERSION` must only represent actual application releases (e.g., `0.1.0`, `0.2.0`). Do not use `APP_VERSION` to track implementation milestones of single Business Objects. Use Git tags (e.g., `v0.2.0-company`) for tracking implementation milestones instead.
- **Terminology**: Never refer to `accounting.py` as the "legacy reference implementation." Instead, call it the **Historical Baseline**. AaramBooks is the authoritative implementation backed by documented business rules, verified source data, and automated regression tests.
- **Connector Isolation**: Do not hardcode the observed URLs or assumptions into the business logic. Isolate all ShopDeck-specific endpoints, authentication, and request formats inside `ShopDeckConnector`, so future UI or API changes affect only the connector implementation and not the rest of AaramBooks.
- **Inventory Certified Baseline**: The core Inventory logic (BOM, Transformation, Job Work, Receipts, DB Isolation) is now fully certified and baselined in `docs/INVENTORY_CERTIFIED_BASELINE.md`. From this point onward, whenever Antigravity proposes a new Inventory feature, it must explicitly state: **"Which existing certified invariants does this change touch, and which certification/regression tests will be rerun?"**
- **AI Handoff File — Mandatory Read**: At the start of every session, read `AI_HANDOFF.md` at the project root before making any changes. It is the single source of truth for project state across AI model switches.
- **AI Handoff File — Incremental Updates**: Do NOT wait until the end of a task to update `AI_HANDOFF.md`. Update Section 15 (Current Project State) after every significant step — e.g. after implementing a new method, after passing a test, after completing a sub-task. This ensures that if the model is exhausted or the session ends unexpectedly, the next AI agent can continue from the last known good state without requiring the human owner to explain what happened.
- **Bug Documentation**: Every time a major bug is encountered and resolved, it MUST be proactively documented in `docs/INVENTORY_BUGS_RESOLUTION_REPORT.md` including the symptoms, root cause, failed attempts, and the successful resolution. Further, when a persistent bug or similar bug appears in future you must refer to it for probable solutions.
- **STRICT PERMISSION RULE (CODE MODIFICATION)**: Do NOT modify ANY application code across workspaces (especially outside of the primary Inventory workspace, like Packer) without asking for EXPLICIT user permission first. Even if a solution is obvious, you must present the solution to the user and wait for their explicit "go ahead" before executing any file modifications.
